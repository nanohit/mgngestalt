# Магнитогорское гештальт-сообщество

[Сайт](https://mgngestalt.vercel.app) · [Примеры интерфейса](https://mgngestalt.vercel.app/?demo=1) · [Кабинет](https://mgngestalt.vercel.app/cabinet)

Адаптивный сайт на HTML, CSS и нативных ES-модулях. **Без фреймворков, npm-зависимостей, сборщика, внешних шрифтов и аналитики.** Node.js нужен только для служебных скриптов и одной Vercel Function. `npm run build` просто копирует `public/` в `dist/` и закрепляет CDN-ссылки на логотипы за коммитом.

## Как работает

- Посетитель без регистрации читает `data/site.json` из ветки `content` через статическую выдачу GitHub. Поиск, фильтры, календарь и профили работают в браузере. Запасные источники — jsDelivr, Fastly jsDelivr и сохранённый снимок в самом сайте.
- HTML/CSS/JS размещены на Vercel. Логотипы и опубликованные фотографии загружаются с jsDelivr; для логотипов есть локальный запасной путь. Для удобной адресной строки нужен обычный сайт на Vercel: jsDelivr раздаёт файлы и не заменяет HTML-хостинг. Туннель не нужен, доступен постоянный `*.vercel.app`.
- Только кабинеты вызывают `/api/account`. Эта одна небольшая serverless-функция проверяет пароли и права, обращается к Upstash REST и записывает публичный JSON в GitHub Contents API. Постоянного сервера нет.
- В Upstash находятся **только** хеши паролей, логины, черновики профилей, сессии и счётчики попыток. Посетитель каталога выполняет **0 команд Redis**.
- Публикация — коммит в отдельной ветке `content`. Актуальный JSON читается из статической выдачи GitHub с общей для посетителей минутной версией URL; jsDelivr остаётся резервом. Для веток [jsDelivr использует долгий кэш](https://github.com/jsdelivr/jsdelivr#caching) и ограничивает повторную очистку, поэтому каталог не зависит от успешного purge. Обновление контента не требует сборки сайта.
- Все фото перед загрузкой сжимаются в браузере в WebP до 720px по длинной стороне и 180 КБ. Файлы неизменяемые: новая фотография получает новый путь. Нет отдельного платного медиа-хранилища.

Публичная ветка не содержит паролей и черновиков. Удалённый из каталога текст или фотография могут оставаться в истории GitHub и CDN: не публикуйте чувствительные личные/медицинские сведения. Это каталог и прямые контакты; сайт не принимает записи, платежи или обращения пациентов.

## Возможности

Один администратор создаёт до 30 кабинетов, сбрасывает пароли, редактирует профили, календарь, описание и контакт сообщества. Пароли создаются случайно и показываются администратору один раз. При первом входе смена пароля обязательна.

Терапевт редактирует только свой профиль, фото, стоимость, формат, темы работы и до четырёх контактов. Публикация включается отдельным флажком. Посетитель может искать по имени/тексту, фильтровать по формату и теме, открыть профиль и связаться напрямую. Даты календаря — **Asia/Yekaterinburg, UTC+5**, местное время Магнитогорска.

`?demo=1` включает исключительно демонстрационные данные с заметным баннером. Никаких вымышленных терапевтов в обычном каталоге нет.

## Подключение рабочих кабинетов

В текущем проекте база Upstash и Production-переменные уже подключены. Данные администратора хранятся локально в игнорируемом Git файле `artifacts/admin-access.local`. Для быстрого запуска серверу передан существующий токен авторизованного `gh`; его права шире одного репозитория. При отдельной настройке используйте ограниченный токен, описанный ниже.

1. Создайте **Free** Redis в [Upstash Console](https://console.upstash.com). Оставьте auto-upgrade отключённым. На момент запуска Free: 256 МБ, 500K команд/месяц, 10 ГБ трафика; проверьте [актуальный тариф](https://upstash.com/pricing/redis). Через Vercel Marketplace Free Redis может отсутствовать — не выбирайте платный план ради подключения.
2. Создайте [fine-grained token GitHub](https://github.com/settings/personal-access-tokens/new): Resource owner `nanohit`, **Only select repositories → mgngestalt**, **Contents → Read and write**. Настройте срок действия и обновляйте токен до истечения. Не используйте персональный токен с доступом ко всем репозиториям.
3. В [Production environment проекта Vercel](https://vercel.com/vfeb8c02646d6999bcd7afce8/mgngestalt/settings/environment-variables) добавьте как Secret:

| Переменная                 | Значение                            |
| -------------------------- | ----------------------------------- |
| `UPSTASH_REDIS_REST_URL`   | REST URL вашей базы                 |
| `UPSTASH_REDIS_REST_TOKEN` | REST Token вашей базы, не Read Only |
| `GITHUB_CONTENT_TOKEN`     | Ограниченный токен из шага 2        |
| `ADMIN_PASSWORD_HASH`      | Хеш первого пароля администратора   |

`GITHUB_REPOSITORY` по умолчанию `nanohit/mgngestalt`, `CONTENT_BRANCH` — `content`, `ADMIN_LOGIN` — `admin`. Для других адресов можно задать `SITE_ORIGIN` с точным origin без завершающего `/`. Если он не задан, проверяется HTTPS origin текущего хоста. Секреты не нужны в браузере и не должны попадать в `public/` или Git.

Для первого администратора владелец запускает `node scripts/setup-admin.mjs`: скрипт создаёт случайный пароль, передаёт **только хеш** через stdin в Vercel и сохраняет первоначальные данные локально в `artifacts/admin-access.local` с правами 0600. Существующий хеш автоматически не перезаписывается. При первом входе администратор меняет пароль; после этого локальный файл первоначального доступа можно удалить.

4. Убедитесь, что ветка `content` существует (`node scripts/init-content.mjs`, запускается один раз).
5. Выполните `vercel deploy --prod --scope vfeb8c02646d6999bcd7afce8`, чтобы новая версия получила Production secrets. Откройте `/cabinet`. Создайте первого участника, передайте пароль лично и проверьте публикацию.

Для локальной разработки можно задать отдельные тестовые доступы в `.env.local` (игнорируется Git). Используйте отдельную БД и ветку: локальные сохранения с Production-ключами меняют настоящий каталог. `npm run dev` не эмулирует авторизацию — подключает реальное хранилище, если оно настроено.

## Запуск и проверки

```sh
npm run dev   # http://127.0.0.1:4173
npm run check # синтаксис JS и JSON
npm test      # пароли, права, обязательная смена, публикация, сброс, удаление, лимиты
npm run build # статические файлы в dist/
```

Тесты проверяют полный сценарий функции с изолированными HTTP-адаптерами Redis/GitHub. Они не подменяют кабинеты в опубликованном сайте и не доказывают доступность реальных провайдеров. На рабочем сайте проверены вход администратора, обязательная смена пароля, создание и сброс кабинета, публикация фото и контактов, права, конфликт версий и редактирование календаря. Тестовые аккаунты и мероприятия удалены.

## Защита и ограничения

- `scrypt` с индивидуальной случайной солью; хеши только на сервере.
- Случайные токены сессий; Redis хранит SHA-256 токена, cookie HttpOnly + Secure + SameSite=Strict, срок 7 суток.
- Смена и сброс пароля увеличивают версию аккаунта и немедленно отменяют старые сессии.
- Все записи принимают JSON и требуют совпадения Origin. Права, лимиты, входные данные и принадлежность профиля проверяются сервером.
- Ограничены попытки входа по IP и логину, действия аккаунтов и число терапевтов. Глобальный короткий lock и ревизии предотвращают потерю одновременных изменений.
- Вывод данных экранируется; контакты допускают только HTTP(S), tel и mailto. CSP исключает inline-скрипты и встраивание сайта.
- При сбое GitHub заполненный профиль остаётся черновиком в Redis, кабинет предлагает повторить сохранение. Для календаря и настроек используется проверка версии публичного JSON.
- Нет постоянных фоновых процессов, cron, polling посетителей или расходов на каждую карточку. Защиту от крупного DDoS обеспечивает платформа; злоумышленник всё ещё может расходовать бесплатные лимиты функцией входа.

Хранение 30 профилей и сессий намного ниже Free-лимитов; это оценка объёма, не обещание бессрочного бесплатного тарифа. **Vercel Hobby ограничен личным некоммерческим использованием.** Если сайт используется для продвижения платных услуг, проверьте [Fair Use Guidelines](https://vercel.com/docs/limits/fair-use-guidelines): может потребоваться Pro. Код переносим: статика + обычный Node handler + HTTP Redis/GitHub, привязки к платному фреймворку нет.

## Резервные копии и сопровождение

Публичный контент имеет историю GitHub; резервируйте Redis отдельно через Upstash backup/export. Изменения основных файлов идут в `main`, публикации — в `content`. При подключении Git integration в Vercel отключите автодеплои для `content` (в `vercel.json` уже задан `ignoreCommand`). Для восстановления контента откатите `data/site.json` в ветке `content` и очистите CDN-кэш. Не публикуйте дампы Redis в открытом репозитории.
